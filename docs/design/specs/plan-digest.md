# Plan binding: plan_digest, target_digest, execution_digest

M4a of the plan-binding work. `plan` returns three digests; `execute` derives the plan
again from the same inputs and refuses anything that does not match, before it signs
anything. Everything is computed over `cic-canonical-json/1` (`canonical-json.md`).
Go implements it (`module/plan_binding.go`); the **normative expectations are the
language-neutral vectors** in `module/testdata/plan_digest_vectors.json`, generated by
an independent implementation (no Go), so another implementation can be checked
against the same file.

Status: **implemented** in the module (derivation, the three digests, the gate in
`execute`). Approval, authority and single use of a plan are **concept** (M4b, the
Relay): nothing here provides them.

## What it proves, and what it does not

A request whose plan, desired state, observed state and target agree with each other,
and with the plan the provider derives from them again, is **internally consistent**.
That is all. It does not show that anyone approved the plan, that the caller may run
it, that the key belongs to the right tenant, or that it has not run before. A caller
who can change every input and every digest builds another consistent request. The
Relay must verify an approval that names `execution_digest` (M4b); until it does, a
consistent request runs (pinned by `TestM4aDoesNotClaimApproval` and
`TestM4aDoesNotPreventReplay`).

## The three digests

Each is `sha256:` and 64 hex digits over the canonical JSON text of an envelope. The
envelope is a JSON object, so every field is delimited by the JSON structure; nothing
is built by joining strings. Each has its own domain tag (`v`), so objects of
different roles never share a hash namespace.

- **`plan_digest`** (`v` = `cic-oracle-execution-plan/1`): everything the plan will
  execute. Members: `contract`, `desired`, `kind`, `observed`, `operation`,
  `provider_operations`, `v`.
  - `desired` / `observed`: `data` (the canonical form of the payload's JSON),
    `encoding`, `schema_hash`, `schema_id`, `schema_version`.
  - `provider_operations`: the ordered list of `{method, operation, path}`.
  - `contract`: the digest of the kind's registry contract (below).
- **`target_digest`** (`v` = `cic-oracle-execution-target/1`): where it runs. Members:
  `base_path`, `host`, `key_id`, `kind`, `resource_id`, `revision`, `v`. `host` and
  `key_id` are strings; `base_path`, `resource_id` and `revision` are `null` when
  empty (an absent field and an empty one are the same value, by rule).
- **`execution_digest`** (`v` = `cic-oracle-execution/1`): `{plan_digest,
  target_digest, v}`. It binds the two, so a plan cannot be paired with another,
  equally valid, target. It is the value an approval will name.

Not in `plan_digest`: the `reason` of an operation and the plan's `notes`. They are
explanation; nothing executes or decides on them, and they can change without changing
the digest, on purpose. If any decision, policy or approval rule ever reads them they
must move into the envelope; an audit that must keep their exact text needs its own
evidence digest or signed record.

The `contract` digest covers what shapes a plan or an execution in the kind's
registry: its operations (name, method, path template, role) and fields (policy, JSON
type, action) and required fields. A module version that maps a change to other
operations has another contract digest, so an older plan no longer matches.

The name `plan_digest` is not the engine's `conformance_plan_digest`: that digests a
conformance plan and is a different thing. The domain tag keeps them apart.

## Plan: the lifecycle and the target

`plan` takes a `target` (`host`, `base_path`, `key_id`, `resource_id`, `revision`).
`host` and `key_id` are required and every field is bounded (1024 bytes);
`resource_id`, when present, must be a well-formed OCID of the kind. Whether a
resource id is required follows the lifecycle:

| observed | `target.resource_id` | Result |
|---|---|---|
| empty | empty | a **create** plan: `operation: create`, the kind's create operation |
| empty | present | refused (`observed.data`): a named resource has state |
| state | empty | refused (`target.resource_id`): an existing resource needs its id |
| state | present | the diff: `noop`, `update`, `action` or `replace` |

The second row keeps the guard from cic-module-oracle-cloud#31: an empty observed
state can no longer be read as "every field changed" for a resource that was never
created.

## Execute: the gate

After the M1 id check and the M3 registry check, and before the first `sign`:

1. `plan.plan_id` must be absent (it is retired; `plan.plan_id` otherwise);
2. `plan.plan_digest`, `plan.target_digest`, `plan.execution_digest`, `desired` and
   `observed` must be present;
3. the plan is **derived again** from `desired`, `observed` and the binding, and must
   have the same `operation` and the same provider operations (name, method, path, in
   the same order) as the plan received: swapping an update for an M3-valid delete is
   caught here, not only by a digest;
4. the three digests must equal the ones computed from the request;
5. `config.data` must be the same JSON value as `desired.data` (canonical equality);
6. only then the first step is signed. The result echoes `execution_digest`.

Every refusal is `validation`, makes no sign and no actuate call, and names the
dimension in `field_path` (`plan.operation`, `plan.provider_operations[i]`,
`plan.plan_digest`, `plan.target_digest`, `plan.execution_digest`, `config.data`,
`desired.data`, `observed.data`, `binding.*`).

## Compatibility

`plan_id` is retired: `plan` no longer emits it and `execute` refuses a request that
carries one (even an empty or null one). No alias: an alias would be a way around the
digest check. A survey of the locally cloned CentralInfraCore repositories and the
cic-factory found no consumer of the module's `plan_id` (only a length check in this
module's own test); repositories not cloned here and other environments were not
checked.
